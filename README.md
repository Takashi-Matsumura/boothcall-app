# BoothCall

展示会ブースでコーヒーを提供する際の「待ち時間」を管理するための呼出システムです。来場者にはFeliCa(NFC)カードを引き取り券として手渡し、スタッフがカードのタップでチケットの発行・引き換えを行い、大型ディスプレイに呼び出し状況を表示します。

## 画面構成

| 画面 | パス | 用途 |
| --- | --- | --- |
| サイネージ表示 | `/display`(`/` からリダイレクト) | ブースの大型モニターに常時表示。呼び出し中の番号を巨大表示し、準備中の番号一覧を表示する |
| スタッフ操作 | `/admin` | NFCカードのタップによる注文発行・引き換え、呼び出し・スキップ・削除・全リセットを行う |

## 主な機能

- チケット発行 → 準備中 → 呼び出し中 → 完了(渡済み/スキップ) のステータス管理
- **FeliCa(NFC)カードによる引き取り券管理**: 約100枚のカードを使い回す運用を想定。カードのタップは「識別・選択」のみを行い、状態変更は画面上のボタンで確定する
- **カードごとの恒久整理番号(映画館の半券方式)**: 各物理カードには最初にタップされた時点で恒久的な番号が1回だけ割り当てられ(サーバ再起動をまたいで保持)、その番号をシール等に書いてカードに貼る運用を想定。以降そのカードは何度再利用されても常に同じ番号で呼ばれるため、紙の半券が無くても客が自分のカードと呼出番号を結びつけられる
- **注文コーヒーの記録・確認・集計**: 発行は「カードのタップ→注文の品をタップ」の2アクションで完結し、その場でコーヒーの種類(1チケットにつき1種類)を記録する。呼び出し・引き渡し時はチケットカード上の品名チップで注文内容を確認でき、選択ミスがあれば渡済みにするまで同じチップから訂正できる。管理画面の「注文集計」から種類別の注文数・渡済み数を確認できる
- **名刺受け取りゲート**: 担当者の名刺を受け取っていることを「渡済み」操作の必須条件とし、サーバ側で厳格に強制する(スタッフによる上書き手段はない)
- Server-Sent Events (SSE) による `/admin` と `/display` 間のリアルタイム同期(切断時は自動でポーリングにフォールバック)
- Web Audio API による呼び出しチャイム(ON/OFF切り替え可能)
- 削除は楽観的UI更新 + Undoトースト、全リセットは誤操作防止の2段階確認

## セットアップ

```bash
npm install
npm run dev
```

[http://localhost:3000](http://localhost:3000) を開くと `/display` にリダイレクトされます。スタッフ操作は [http://localhost:3000/admin](http://localhost:3000/admin) から行います。

その他のコマンド:

```bash
npm run typecheck  # 型チェック
npm run lint       # ESLint
npm run build      # 本番ビルド
npm run start      # 本番サーバ起動
```

## NFCカードリーダーのセットアップ(Sony RC-S300)

このアプリはブースの管理PC上で動かす **Next.jsサーバ自身** が、PC/SC経由でUSB接続されたRC-S300を直接読み取ります(別プロセスのブリッジは不要です)。

- **macOS**: Xcode Command Line Tools(`xcode-select --install`)が必要です。PC/SCサービスはOS標準で組み込まれているため、他のインストールは不要です。macOS 13以降ではRC-S300のドライバも不要でOS標準のCCIDドライバで認識されます。
- **Windows**: Visual Studio Build Tools(「C++によるデスクトップ開発」ワークロード)とPython 3が必要です(`nfc-pcsc`のネイティブビルド用)。また、Sonyの「NFCポートソフトウェア」ドライバがデバイスを排他的に掴んでPC/SCから見えなくすることがあるため、デバイスマネージャで「スマートカードリーダー」配下(標準CCIDドライバ)に認識されていることを確認してください。Smart Card Service(`SCardSvr`)が自動起動になっているかも確認してください。
- カードをタップすると `/admin` 画面上部のパネルに検出結果が表示されます。**未登録のカードなら「この番号で登録する」ボタンでそのカードへ恒久番号を割り当て**(展示会前に100枚をタップして回るセットアップを想定。割り当てられた番号をその場でシールに書いてカードに貼ってください)、登録済み・未紐付けのカードなら**注文の品(コーヒーの種類)ごとのボタン**から選ぶとその場で注文が発行され、既存の注文に紐づいたカードなら該当のチケットカードへ自動的にスクロール・ハイライトされます。
- 登録済みカードの一覧は `/admin` の「登録済みカード」の折りたたみから確認できます。誤登録の取り消し(削除)もここから行えます。カードが破損・紛失し、同じ番号を新しいカードへ引き継がせたい場合は `PATCH /api/cards/<古いカードのIDm>` に `{"newCardId": "<新しいカードのIDm>"}` を送ってください(頻度が低いため専用UIは用意していません)。
- コーヒーのメニュー項目は `lib/menu.ts` の固定リストで管理します(サンプルとしてブレンド・カフェラテ・カプチーノを登録済み)。当日のメニューに合わせて変更する場合はこのファイルを編集してください。各チケットカード上の品名チップは、渡済みになるまで(PREPARING・CALLING の間)タップして選び直せます — 選択ミスの訂正手段です。渡済み後の注文内容は変更できません(集計の実態とずれるため)。種類別の注文数・渡済み数は `/admin` の「注文集計」の折りたたみから確認できます。
- 開発環境にリーダーが無い場合でも、開発専用の擬似タップAPI(`POST /api/nfc/scan`、本番ビルドでは404になる)でロジックを検証できます。

**展示会前に必ず現地の実機で確認してください**(このAPIレベルでの動作確認だけでは検証できない項目です):

- 実際のカードのIDm読み取り(`BOOTHCALL_NFC_DEBUG=1 npm run start` でログを確認)
- カードの連続タップ・置きっぱなし時の挙動(冷却時間はコードで1.5秒に設定、必要なら調整)
- リーダーの抜き差しに対する接続状態バッジの追従
- 100枚のカード全てが問題なく読み取れること

## 運用上の注意

- チケット(注文)の状態は **サーバプロセスのメモリ上にのみ保持** されます。サーバを再起動すると発行済みチケットは全て消去されます(展示会1日単位の運用を想定した割り切りです)。「全リセット」操作も同様にチケットのみを消去します。**注文集計(種類別の注文数・渡済み数)もチケットから都度算出しているため、同様にサーバ再起動・全リセットで0にリセットされます** — 展示会終了後の集計は、再起動する前に確認・記録してください。
- **カードごとの恒久番号(`data/card-registry.json`)だけは例外的にディスクへ永続化され、サーバ再起動や「全リセット」をまたいで保持されます。** 一度シールを貼ったカードの番号を失わないようにするための唯一の永続化データです。**このファイルを誤って削除しないでください** — 削除すると、既にシールを貼ったカードが次にタップされた際に「未登録」として扱われ、別の番号が再割り当てされてしまいます(貼り直したシールとシステム上の番号がずれる)。展示会前にバックアップを取ることを推奨します。
- **認証機能はありません。** ブースのPC1台 + LAN上での運用を前提としており、同一ネットワーク上からは誰でも `/admin` の操作やAPIを呼び出せます。インターネット等の信頼できないネットワークに公開する構成では使用しないでください。
- **単一プロセス(`next start`)で運用してください。** PC/SCのリーダーは排他アクセスのため、複数プロセス・クラスタ構成にすると一方がカードを読めなくなります。
